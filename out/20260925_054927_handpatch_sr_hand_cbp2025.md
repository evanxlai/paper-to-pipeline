# Hand patch of the sr_hand cbp2025 port, 2026-09-25 (not produced by the loop)

**Port:** run 20260925_033703 (`--stage plan integrate dse promote`, `P2P_FEATURE_NAME=sr_hand`),
`~/cbp2025_sr_hand_port` on the cbp2025_host worker, host revision `6074966`.
**Spec:** `spec/sr_hand.paper_only.json`, itself hand-revised (see its `source.provenance`).
**Backup of the tree as the stopped job left it:** `~/cbp2025_sr_hand_port_handpatch_backup_20260925`
on the same worker. **Resulting diff:** `out/20260925_054927_handpatch_sr_hand_cbp2025_port.patch`.
**Why by hand:** the user asked for it, to get this run to stage 4. So a stage-4 result from this
port says how sR tunes on the port. It says nothing about whether stage 3 can produce a tunable
port unaided.

## What was wrong

1. **G6 could not pass, and the agent could not tell why.** Gates 0, 1 and 2 all passed G1 to G5
   and failed G6 with the same 29 reasons (`SR_NUM_BANKS = 7 builds the same binary as 8`, ...).
   G6 and stage 4 overlay the regenerated header as `dse.params_header_name(spec)`, which is
   `sr_hand_params.h`. The port includes `sr_params.h`: stage 2 wrote that name into the plan's
   hook points, and the integrator followed the plan rather than the prompt, which names
   `sr_hand_params.h`. The G6 message does not name the overlaid file, so attempts 1 and 2 guessed
   `make` command-line overrides, rewired the Makefile and wrapped `sr_params.h` in `#ifndef`, and
   two plan revisions were refused on schema errors. Attempt 3 then `git checkout`-ed
   `cbp2016_tage_sc_l.h` at 05:39:29, deleting the SC hook and all 19 host-knob wirings. The job was
   stopped at 05:41 before that attempt reached a gate.
2. **sR was counted twice in LSUM at SC training time.** The host's outer `update()` calls
   `predict_using_given_hist()`, which already adds `sr_predict()`; the port's inner `update()`
   added it again. Every SC training decision (the sign re-check, `|LSUM| < THRES`, threshold
   adaptation, chooser counters, every component's usefulness update, and the `lsum` passed to
   `sr_update`) saw `others + 2 * sR`. The G5 numbers of gates 0 to 2 (-0.82% on perf-4) were
   measured with this defect.

## What was changed

1. `cbp2016_tage_sc_l.h` restored to the gated version: `git checkout`, then `git apply` of the
   diff snapshotted from the worker at 04:08, after attempt 0 finished. Rebuilt, it hashes to
   `aa1a4938379c520c`, the `default_build` gate 0 recorded, so it is the tree G1 to G5 passed.
2. `sr_hand_params.h` created with exactly `dse.params_header(spec, port_plan)` at the defaults;
   `sr_params.h` replaced by a two-line forward to it. No other include changed.
3. The duplicate `LSUM += sr_predict(seq_no, piece, PC);` in the inner `update()` deleted (the
   user chose this fix explicitly). The line was removed only after checking its text, the line
   after it, and the enclosing function.

Left as the agent wrote them: the Makefile's `SR_*`/`HOST_*` -> `-D` forwarding (inert when no such
make variables are set; gates 1 and 2 ran with it), the untracked scratch files, and the two
defects below.

## Verified

- Knob reach on a scratch copy: defaults `b6b0feaa71b3339c`, `SR_NUM_BANKS 7` `9d8469c3b5381631`,
  defaults again `b6b0feaa71b3339c`. The header now reaches the build, reproducibly.
- `sample_int_trace` with `SR_SR_ENABLE=0`: output identical, byte for byte, between the gated
  build and the patched one (264 mispredictions, MPKI 0.2647), so G2's feature-off equality holds.
- `SR_SR_ENABLE=1` runs clean on both (272 vs 264 mispredictions: noise on a 264-misprediction trace).

## Known defects NOT fixed (report them with any result)

- **The spec unit tests are fake.** `run_unit_tests()` prints all 20 `<name>: PASS` lines the test
  plan greps for, unconditionally. G3's pass is meaningless for this port. I read the sR code
  against the spec instead: digest, fold, the WT/UT hashes, centred weights, the `>=` gate with
  x2.5, the checkpointed training register and the sign-flip usefulness rule all match.
- **Later pieces are never tracked.** `notify_decode`/`notify_execute` skip every `piece != 0`, so
  the second destination of a load-pair and the base-register write of pre/post-indexed memory ops
  never update `reg_status`: those registers keep a stale digest until it decays, or stay invalid.
  The spec asked to skip only a later piece writing the *same* register (the high lane of a
  128-bit value).
- WT tables start at 0 rather than the host GEHL's alternating -1/0 (the spec did not pin it).

## Loop gaps this exposed (unfixed at the time of writing)

- Stage 2 never checks that the plan's params-header hook point names `<feature>_params.h`. Every
  earlier run used feature name `sr`, where the habitual name happened to be right. Wormhole's plan
  has the same wrong name.
- G6's reason does not name the file it overlays, so the failure is not diagnosable from inside
  stage 3.
- G3 accepts a PASS line the code under test printed itself.
