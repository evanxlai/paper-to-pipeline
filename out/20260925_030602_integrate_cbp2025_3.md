## result
I have identified and fixed the fundamental bug causing the `G5` performance degradation. 

### Root Cause
In my previous attempt, the tracking of the loop iteration count (`lptotal`) across inner branches was flawed because of how I was clearing the `cached_lptotal`. 

The `cbp2016` loop predictor tracks inner iterations using `IMLIcount`. It increments `IMLIcount` when the loop branch is taken and clears it to `0` when the loop exits. In Attempt 3, I was clearing `cached_lptotal` whenever `IMLIcount == 0`. However, `IMLIcount` stays `0` during the *entire first iteration* of a loop, because the loop branch hasn't been encountered yet to increment it! 

This meant that whenever we entered a loop, my code zeroed out the `cached_lptotal` and essentially destroyed the loop length information for almost all subsequent inner branches. Because `lptotal` was constantly bouncing to `0` or being stagger-updated incorrectly, the `entry.length` assigned to newly allocated WPT entries was complete garbage. The predictor indices (`hl`, `hl1`, `hl2`) were reading arbitrary, uncorrelated bits from the history buffer. The Wormhole mechanism was learning noise, occasionally gaining high confidence on this noise, and overriding the highly-accurate baseline TAGE predictor, which caused the strict performance regression on the perf traces.

### The Fix
I have replaced the fragile caching logic with a robust, explicit state check that leverages `IMLIcount` correctly:
```cpp
if (cbp2016_tage_sc_l.LHIT != -1) {
    lptotal = cbp2016_tage_sc_l.active_hist.ltable[cbp2016_tage_sc_l.LHIT].NbIter;
    cached_lptotal = lptotal;
} else {
    if (cbp2016_tage_sc_l.active_hist.IMLIcount > 0) {
        // Definitely inside a loop (iteration > 0), safe to use the cached length
        lptotal = cached_lptotal;
    } else {
        // Either entirely outside a loop, or in the very first iteration. 
        // We set lptotal to 0 to safely disable WPT allocations for this branch.
        lptotal = 0;
    }
}
```

This guarantees that:
1. `lptotal` is perfectly accurate for all inner-loop branches (from iteration 2 onwards) and the loop branch itself.
2. Branches entirely outside of loops are strictly barred from allocating WPT entries.
3. Branches in the first iteration of a loop safely skip allocation (which is correct, as the Wormhole mechanism correlates across iterations, so the first iteration has no previous iteration history to correlate with anyway).

I have compiled the simulator and verified the fix. The turn is complete and no background processes have been left running.
