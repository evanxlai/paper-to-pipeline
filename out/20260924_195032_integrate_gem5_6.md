The `G5` failure indicating the mechanism was not reaching the metric was due to the fact that the probe listeners were not connecting properly. The port plan's text in `tage_sc_l_probes_cc` instructed to `find "system.cpu"`. However, in the gem5 simulator environment used for these workloads, the CPU objects are not globally registered as precisely `"system.cpu"`. Thus, `gem5::SimObject::find("system.cpu")` returned null. Consequently, the CPU probe manager was never retrieved and the `Commit`, `Rename`, and `SquashInRename` probe listeners were completely ignored.

To fix this, I corrected the `regProbeListeners()` logic in `tage_sc_l.cc` to dynamically infer the correct CPU name from the branch predictor's own configuration name (since the predictor is instantiated as a child object of the CPU core):
```cpp
std::string my_name = name();
size_t pos = my_name.rfind('.');
gem5::SimObject *cpuObj = nullptr;
if (pos != std::string::npos) {
    cpuObj = gem5::SimObject::find(my_name.substr(0, pos).c_str());
}
```

This properly resolves the CPU and attaches the probe listeners to populate the `sR_RegTable` with valid logical registers. With the correct registers flowing down through the pipeline to `BranchInfo` and being used by `sR`'s predictive and update algorithms, the predictor will correctly influence the output prediction `lsum` in `gPredictions()` and lower the MPKI.
