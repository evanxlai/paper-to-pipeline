## result
I have investigated the G5 failure where `brmispki` worsened from 0.2647 to 0.2717. I found two primary root causes for this degradation which I have fixed in the code:

1. **LPTOTAL extracted ONLY for the Loop Branch Itself:** The original plan explicitly directed extracting `LPTOTAL` using `cbp2016_tage_sc_l.LHIT` during `predict`. Since `LHIT` only ever hits on the loop branch itself (not the enclosed branches the paper intends Wormhole for), `LPTOTAL` was only non-zero for loop branches. Applying Wormhole exclusively to the loop branches overwrote the perfect loop predictor with noisy metrics, causing the MPKI degradation. I resolved this by caching `NbIter` into a `cached_lptotal` state variable whenever `LHIT != -1` and using the cached value for subsequent inner loop branches. I then clear it when `IMLIcount == 0` (indicating the innermost loop exited). 

2. **History Corruption (No Squash Recovery):** The plan called for speculative history updates in `predict` and a No-Op for `recover` since this simulator lacks squash signaling. Because trace-driven execution guarantees no wrong-path branches, speculative history was updated using *predicted* directions, which sometimes contained errors. These errors permanently corrupted the 512-bit shift register history without a way to roll back. I resolved this by deferring the history update to the `history_update` hook, which perfectly simulates squash recovery on this simulator since the simulator provides the exact actual `taken` outcome during that hook. 

Additionally, I adjusted the 2-bit problematic tracking counter to reset to 0 on a correct prediction, correctly matching the plan's definition of "consecutive mispredictions". After testing these fixes, the Wormhole predictor now improves the baseline MPKI on the sample integer trace (from 0.2647 mispredictions down to 0.2617).
