# CBP2025 (6th Championship Branch Prediction) — verified infrastructure report

## 1. Where the official framework lives

- **Official simulator repo: `https://github.com/ramisheikh/cbp2025`** (Rami Sheikh, ARM; repo description "Championship Branch Prediction 2025"). Default branch `main`, created 2025-01-22, last push 2025-05-19, 75 stars / 58 forks. This is the repo linked from the official "CBP2025 Simulator Framework" page at `https://ericrotenberg.wordpress.ncsu.edu/cbp2025-simulator-framework/` (competition home: `https://ericrotenberg.wordpress.ncsu.edu/cbp2025/`; workshop was June 21, 2025 @ ISCA-52, Tokyo).
- Code carries per-file licenses (ARM Ltd BSD-3 headers on `cbp.h`/`cond_branch_predictor_interface.cc`, NCSU BSD-3 on `sim_common_structs.h`/Makefile, public-domain/unlicense on `trace_reader.h`, which is derived from the CVP trace reader by Arthur Perais, "updated for CBP" by Saransh Jain/Rami Sheikh). No repo-root LICENSE file.

## 2. Build & run

```
make clean && make        # g++ -std=c++17 -O3; links -L./lib -lcbp -lz (lib/ builds first via sub-make)
./cbp                     # prints usage
./cbp trace.gz            # run one trace
./cbp -E 1000000 trace.gz # periodic misprediction stats every 1M instrs
```
Other CLI flags parsed in `lib/cbp.cc::parseargs` (all optional, trace file required): `-d` perfect D-cache, `-b` perfect branch prediction (all types), `-P` enable stride prefetcher in L1D, `-M <num_ldst_lanes>`, `-A <num_alu_lanes>`, `-F <fetch_width>,<fetch_num_branch>,<fetch_stop_at_indirect>,<fetch_stop_at_taken>,<fetch_model_icache>`, `-I <log2_ic_size>,<ic_assoc>,<ic_blocksize>`, `-D <13 cache/memory params>`, `-w <window_size>`, `-E <epoch_insts>`.

Default simulated machine (printed at run start): `WINDOW_SIZE=1024, FETCH_WIDTH=16, FETCH_NUM_BRANCH=16, FETCH_STOP_AT_INDIRECT=1, FETCH_STOP_AT_TAKEN=1, FETCH_MODEL_ICACHE=1, PERFECT_BRANCH_PRED=0, PERFECT_INDIRECT_PRED=1, PIPELINE_FILL_LATENCY=10, NUM_LDST_LANES=8, NUM_ALU_LANES=16`; I$ 128KB/8-way/64B, L1$ 128KB/8-way/64B/3-cyc, L2$ 4MB/8-way/64B/12-cyc, L3$ 32MB/16-way/128B/50-cyc, memory 150-cyc; stride prefetcher on; oracle memory disambiguation. Contestants predict conditional branches only; all other branch types get perfect prediction.

## 3. Predictor interface (exact, from `cbp.h` — "must remain unchanged")

Nine free functions (C linkage-style, not a class), called as instructions flow down the pipeline:
```cpp
extern void beginCondDirPredictor();
extern void notify_instr_fetch(uint64_t seq_no, uint8_t piece, uint64_t pc, const uint64_t fetch_cycle);
extern bool get_cond_dir_prediction(uint64_t seq_no, uint8_t piece, uint64_t pc, const uint64_t pred_cycle);   // conditional branches only; returns predicted direction
extern void spec_update(uint64_t seq_no, uint8_t piece, uint64_t pc, InstClass inst_class, const bool resolve_dir, const bool pred_dir, const uint64_t next_pc); // ALL branches, right after prediction — for GHR/LHIST speculative update
extern void notify_instr_decode(uint64_t seq_no, uint8_t piece, uint64_t pc, const DecodeInfo& _decode_info, const uint64_t decode_cycle);
extern void notify_agen_complete(uint64_t seq_no, uint8_t piece, uint64_t pc, const DecodeInfo& _decode_info, const uint64_t mem_va, const uint64_t mem_sz, const uint64_t agen_cycle);
extern void notify_instr_execute_resolve(uint64_t seq_no, uint8_t piece, uint64_t pc, const bool pred_dir, const ExecuteInfo& _exec_info, const uint64_t execute_cycle); // resolve + predictor update happens here
extern void notify_instr_commit(uint64_t seq_no, uint8_t piece, uint64_t pc, const bool pred_dir, const ExecuteInfo& _exec_info, const uint64_t commit_cycle);
extern void endCondDirPredictor();
```
This replaces the old CBP2016 `GetPrediction/UpdatePredictor/TrackOtherInst` PREDICTOR-class API — CBP2025 is pipeline-stage-notification style (derived from CVP infrastructure). `(seq_no, piece)` is the unique instr id (sample combiner: `(seq_no << 4) | (piece & 0xF)`, `piece < 16` for micro-op pieces).

Supporting structs in `lib/sim_common_structs.h`:
- `enum class InstClass : uint8_t { aluInstClass=0, loadInstClass=1, storeInstClass=2, condBranchInstClass=3, uncondDirectBranchInstClass=4, uncondIndirectBranchInstClass=5, fpInstClass=6, slowAluInstClass=7, undefInstClass=8, callDirectInstClass=9, callIndirectInstClass=10, ReturnInstClass=11 }` plus helpers `is_br/is_cond_br/is_load/is_store/is_mem/is_uncond_ind_br/is_uncond_br`.
- `struct DecodeInfo { InstClass insn_class; std::vector<uint64_t> src_reg_info; std::optional<uint64_t> dst_reg_info; }`
- `struct ExecuteInfo { DecodeInfo dec_info; std::optional<bool> taken; uint64_t next_pc; std::optional<uint64_t> taken_target, mem_va, mem_sz, dst_reg_value; }` — note `dst_reg_value` exposes executed register values (enables data/register-value-aware predictors, e.g. the RUNLTS entry).

### How a contestant plugs in
`cond_branch_predictor_interface.cc` (editable, signatures fixed) statically instantiates two predictors and wires them:
- `cbp2016_tage_sc_l.setup()/.predict(seq_no,piece,pc)/.history_update(...)/.TrackOtherInst(pc,br_type,pred_dir,resolve_dir,next_pc)/.update(seq_no,piece,pc,resolve_dir,pred_dir,next_pc)/.terminate()` (from `cbp2016_tage_sc_l.h`).
- Contestant class in `my_cond_branch_predictor.h`: `class SampleCondPredictor` with `setup(); terminate(); bool predict(uint64_t seq_no, uint8_t piece, uint64_t PC, const bool tage_pred); bool predict_using_given_hist(...); void history_update(uint64_t seq_no, uint8_t piece, uint64_t PC, bool taken, uint64_t nextPC); void update(uint64_t seq_no, uint8_t piece, uint64_t PC, bool resolveDir, bool predDir, uint64_t nextPC);` instantiated as `static SampleCondPredictor cond_predictor_impl;`. Pattern: checkpoint history at predict time into `std::unordered_map<uint64_t, SampleHist> pred_time_histories`, retrieve at update, erase. **Checkpointed history state is NOT counted against the storage budget.**
- `get_cond_dir_prediction` calls TAGE-SC-L then the contestant predictor (which sees `tage_pred`) — the shipped sample simply returns the TAGE-SC-L prediction. Update happens in `notify_instr_execute_resolve` using `_exec_info.taken.value()` and `_exec_info.next_pc`.

Rules: single **192KB storage budget** (keep the 64KB TAGE-SC-L + up to 128KB of new components, or discard it and use the full 192KB); no per-trace algorithm tuning; no causality violations; prediction tables can't be updated with actual outcomes inside the prediction path.

## 4. Trace suite

- **Training set: exactly 105 traces** (verified by counting `reference_results_training_set.csv`: 105 data rows), 6 workload categories: **int 37, web 26, infra 16, fp 14, compress 8, media 4**. Download: Google Drive folder `https://drive.google.com/drive/folders/10CL13RGDW3zn-Dx7L0ineRvl7EpRsZDW` (`pip install gdown; gdown --folder //drive.google.com/drive/folders/10CL13RGDW3zn-Dx7L0ineRvl7EpRsZDW`), distributed as `.tar.xz` bundles containing `<wl>/<name>_trace.gz` files. From the CSV's TraceSize column: **total training set ≈ 14,350 MB ≈ 14.0 GiB of .gz**, avg 137 MB, max 399 MB per trace; total ~4.34B instructions, avg ~41M instrs/trace (official page says 10–130M instrs per trace). Sample traces in-repo are ~1M instrs each.
- **Full set (training + secret scoring traces): Zenodo record `https://zenodo.org/records/15883615`** ("CBP2025 Full Traces", DOI 10.5281/zenodo.15883615, published 2025-07-14, released after the workshop). 7 files, **total 72.69 GiB compressed**: `int.tar.xz` 26.3 GiB, `web.tar.xz` 15.18 GiB, `compress.tar.xz` 12.46 GiB, `infra.tar.xz` 8.79 GiB, `fp.tar.xz` 8.76 GiB, `media.tar.xz` 1.2 GiB, plus `readme.txt` (ARM disclaimer only). **I could not verify a "~673 traces" count or "~160 GiB" figure anywhere** — see caveats.
- **Trace format** (exact comment from `lib/trace_reader.h`; gz-compressed binary record stream, CVP-derived, ARM/aarch64 register model):
```
Inst PC                  - 8 bytes
Inst Type                - 1 byte
If load/storeInst
  Effective Address      - 8 bytes
  Access Size (total)    - 1 byte
  Involves Base Update   - 1 byte
  If Store: Involves Reg Offset - 1 byte
If branch
  Taken                  - 1 byte
  If Taken: Target       - 8 bytes
Num Input Regs           - 1 byte
Input Reg Names          - 1 byte each
Num Output Regs          - 1 byte
Output Reg Names         - 1 byte each
Output Reg Values        - 8 bytes each (INT) / 16 bytes each (SIMD)
```
(Int regs 0-30 GPR, 31 SP, 64 flags, 65 zero; SIMD 32-63.)
- Extra data: "Data Dependent Conditional Branch Characterization" PDF for training traces: `https://ericrotenberg.wordpress.ncsu.edu/files/2025/02/CBP2025-data-dependent-branch-profiles.pdf`.

## 5. Per-trace parallelization

`scripts/trace_exec_training_list.py --trace_dir <dir> --results_dir <dir>`:
- Walks trace_dir for files ending `_trace.gz`; expects layout `<trace_dir>/<workload>/<name>_trace.gz`.
- Runs **one `./cbp <trace>` subprocess per trace via `multiprocessing.Pool()` (`pool.map(execute_trace, my_traces)`)** — default pool = #CPUs; simulator itself is single-threaded per trace.
- Writes each run's stdout to `<results_dir>/<workload>/<name>.log` (skips traces whose .log already exists — resumable), then parses logs into `<results_dir>/results.csv` (pandas).

## 6. Metrics & where they land

Per-run stdout sections (parsed by the script): "DIRECT CONDITIONAL BRANCH PREDICTION MEASUREMENTS" for **Last 10M / Last 25M / "50 Perc instructions" / Full Simulation**, each a row of: `Instr Cycles IPC NumBr MispBr BrPerCyc MispBrPerCyc MR MPKI CycWP CycWPAvg CycWPPKI`. Also branch-type breakdown (CondDirect/JumpDirect/JumpIndirect/JumpReturn/Not control with NumBr/MispBr/mr/mpki), ILP study (instructions/cycles/CycWP/IPC), cache/prefetcher/SQ stats.
- **Warmup: first half of each trace; scoring uses the "50 Perc" (second-half) numbers.** The aggregator prints per-workload-category and overall **arithmetic means of `50PercMPKI` (= BrMisPKI) and `50PercCycWPPKI` (= CycWpPKI)**.
- Competition ranking: **two tracks — BrMisPKI (cond-branch mispredictions per 1K instrs) and CycWpPKI (cycles on wrong path per 1K instrs)**; every entry automatically considered for both. CSV lands at `<results_dir>/results.csv` with columns `Workload,Run,TraceSize,Status,ExecTime,Instr,...,CycWPPKI,50PercInstr,...,50PercCycWPPKI`. Organizer reference numbers on the training set are in `reference_results_training_set.csv` at repo root (e.g. baseline TAGE-SC-L; Seznec's paper reports the 64KB CBP2016 TAGE-SC baseline at 3.750 MPKI and his 192KB CBP2025 TAGE-SC at 3.363 MPKI / 143.935 CycWpPKI on the public traces).

## 7. Baselines shipped

- `cbp2016_tage_sc_l.h` — the CBP2016 winner, **64KB TAGE-SC-L** (Seznec: TAGE + Statistical Corrector + Loop predictor; `#define SC`, `#define IMLI`, `#define LOOPPREDICTOR`, `#define LOCALS/LOCALT`). This is the wired-in default predictor.
- `cbp2016_tage_sc_l_192kb.h` — a **192KB scaled TAGE-SC-L** (NHIST 36, LOGG 11, LOGB 18 bimodal, LOGGNB 12 SC tables) that the organizers added post-submission (Seznec's CBP2025 paper: "the 192KB CBP2016 TAGE component provided by the CBP2025 organizer after the submission ... 3.715 MPKI"). Not included by default; swap the `#include` in `cond_branch_predictor_interface.cc`.
- There are NOT separate 64KB/192KB storage tracks — CBP2025 has a **single 192KB budget** with two metric tracks (unlike CBP2016's 8KB/64KB/unlimited tracks).

## 9. Successor note

A next-gen championship, **CBP-NG** (`https://github.com/AmpereComputing/cbp-ng`, site `https://cbp-ng.bpchamp.com`), uses a completely different API: predictors written against the HARCOM C++ hardware-cost library implementing a `predictor` interface in `cbp.hpp` (`predict1/predict2/reuse_predict1/reuse_predict2`, two prediction levels, energy/latency/area modeling). Ships bimodal/gshare/perceptron/TAGE examples in `./predictors`. Distinct from CBP2025 — don't conflate the two APIs.
